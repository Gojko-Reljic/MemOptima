# MemOptima 0.5.0 Scope

## Purpose

MemOptima 0.5.0 adds a local reader and validator for the evidence artifacts written by 0.4.0. It
turns retained raw observations into a trustworthy, human-readable session summary without adding a
trend, forecast, diagnosis, recommendation, or action capability.

The release answers this narrow operational question:

```text
Is this local MemOptima evidence artifact structurally valid, complete or incomplete, and what
point-in-time container evidence did it retain?
```

Its role in the product control loop is:

```text
Observe → Assess → Retain evidence → Validate and inspect evidence → later: Trend → Forecast
```

## Release boundary

Version 0.5.0 is a Linux-only, local, read-only CLI release. It introduces one command:

```text
memoptima inspect evidence <FILE>
```

`<FILE>` must name an existing regular file that is not a symbolic link. Directories, device files,
FIFOs, standard input, symbolic links, and nonexistent paths are rejected. The command does not
write the file, create a sidecar file, contact a network service, contact Docker, or invoke the
Docker CLI.

The reader processes the JSON Lines artifact one physical line at a time. It never loads the entire
artifact into memory. A single line may be up to the existing 512 MiB artifact limit so every valid
0.4.0 artifact remains readable.

## Supported schema and validation

The reader supports exactly `schema_version: 1`. An unsupported version is a validation error and
is not interpreted on a best-effort basis.

Schema version 1 is closed. Every object must contain exactly the fields defined for its record or
nested object type; an unknown field is a validation error. Required fields must exist, use the
documented JSON type, and satisfy their value constraints. The reader uses a purpose-built C++
validator over the existing JSON parser so it can report stable, precise diagnostics without adding
a JSON Schema dependency.

The validator checks at least:

- each physical line is nonempty valid JSON and its root is an object;
- every record has `record_type` and `schema_version`;
- record types are only `session_start`, `sample`, and `session_end`;
- the sequence is one `session_start`, followed by zero or more `sample` records, followed by at
  most one `session_end` record;
- no record occurs after `session_end`;
- sample sequences are one-based and contiguous;
- `session_end.completed_sample_count` equals the number of accepted sample records;
- a `failed` terminal outcome has a failure object, while `completed` and `interrupted` have
  `failure: null`;
- schema-1 scalar conventions, including decimal strings for 64-bit quantities, `"max"` versus
  `null` limits, bounded numeric PSI averages, and ISO 8601 UTC timestamps with milliseconds; and
- all nested container memory, assessment, diagnostic, warning, finding, and evidence structures.

The reader reports at most 20 validation errors. Each diagnostic identifies the one-based physical
line, a JSON path, and an actionable explanation. A validation error returns exit code `1` and no
summary claiming that the artifact is valid.

## Completion semantics

An artifact that has valid records but no `session_end` is **incomplete**, not invalid. This can
happen after a normal process interruption that could not write its terminal record or after an I/O
failure. The reader preserves and summarizes its valid preceding samples, displays an explicit
incomplete warning, and returns exit code `0`.

An artifact with a valid terminal record is **closed**. Its terminal outcome is displayed as
`completed`, `interrupted`, or `failed`. `interrupted` is a normally handled user stop, not an
invalid or failed artifact.

## Human-readable summary

Successful inspection writes a stable human-readable report to standard output. It includes:

- artifact path and schema version;
- application version and requested sampling contract;
- completion state, terminal outcome when present, and completed sample count;
- first and last capture times when samples exist;
- total discovery-warning count and skipped-container count;
- a container table sorted by full container ID.

Each container row contains its full ID, number of samples in which it appears, highest recorded
assessment risk, number of partial-coverage samples, and the last recorded assessment risk and
coverage. The highest risk is explicitly historical evidence from this artifact. It is not a trend,
a current-state claim, a prediction, or a workload-health result.

The release does not add JSON output for the reader. It does not print every raw sample by default;
the JSON Lines file remains the authoritative raw evidence.

## Safety and privacy boundary

0.5.0 reads only an explicit local evidence file. It does not read `/proc`, cgroupfs, or Docker
state during inspection. It does not change cgroup limits, kernel settings, containers, files other
than its own process memory, or system configuration.

The reader displays only data already present in the artifact. Since artifacts include full Docker
container IDs and cgroup paths, operators must protect them according to their local workload-data
policy. MemOptima does not transmit them.

## Test strategy

The normal Debug and Release suites must provide deterministic coverage for:

- every accepted schema-1 record and nested-object shape;
- unknown fields, missing fields, wrong types, invalid scalar formats, unknown schema versions, and
  invalid record ordering;
- bounded reporting of more than 20 errors;
- contiguous sequence and terminal-count rules;
- closed `completed`, `interrupted`, and `failed` sessions;
- a valid incomplete artifact with preserved summary data and exit code `0`;
- regular-file, symbolic-link, directory, FIFO, and nonexistent-input rejection;
- streaming processing without whole-artifact loading; and
- deterministic container aggregation, risk ordering, partial-coverage counts, and terminal output.

## Acceptance criteria

MemOptima 0.5.0 is complete only when:

- `inspect evidence <FILE>` has a documented and tested CLI contract;
- the reader strictly validates every schema-1 object it accepts and rejects unknown schema versions
  and unknown fields;
- validation diagnostics are bounded, line-aware, and path-aware;
- valid incomplete artifacts remain readable with an unmistakable warning;
- regular-file and symbolic-link safety rules are enforced before content processing;
- the summary does not claim a trend, forecast, diagnosis, health outcome, recommendation, or
  action; and
- Debug and Release suites, Release Valgrind, and the existing quality policy pass.

## Planned evolution

A later release can introduce a machine-readable inspection summary, optional artifact migrations,
and explainable trends derived only from sufficient validated samples. Forecasting, recommendations,
actions, and rollback remain separate future decisions.
