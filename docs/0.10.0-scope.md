# MemOptima 0.10.0 Scope

## Purpose

MemOptima 0.10.0 replaces first-origin, next-sample forecast evaluation with bounded rolling-origin
evaluation of the same memory-current forecast model used by production-facing analysis. It measures
forecast accuracy at fixed operational horizons while keeping collection, analysis, and output
read-only.

It does not claim an OOM prediction, confirm a memory leak, diagnose an anomaly, recommend a
configuration change, or modify a host, container, or cgroup.

## Public Command

The public command remains:

```text
memoptima forecast evaluate <MANIFEST>
```

The schema-version-1 trend manifest remains the input contract. Exit-code categories remain
unchanged: `0` for a valid report, `1` for runtime, input, analysis, formatting, or output failure,
and `2` for invalid command usage.

The human-readable report changes in v0.10. It reports one row per strict container identity,
session-local epoch, and applicable horizon. A machine-readable, versioned JSON evaluation report is
not part of this release.

## Input Integrity

Evidence JSONL records and trend manifests reject duplicate JSON object keys while parsing. The
rule applies to every object, not only schema-defined fields. It follows the I-JSON unique-name
requirement and compares keys after JSON escape decoding, so `"a"` and `"\u0061"` are duplicates.
MemOptima does not apply Unicode normalization to names.

Evidence validation reports `duplicate_key` with the JSONL line, object path, and duplicated key.
Manifest parsing reports the object path and key. The normal terminal-rendering boundary escapes
untrusted diagnostic text before it reaches standard output or standard error.

Evidence records and manifests allow at most 64 simultaneously open arrays or objects. A linear,
zero-allocation pre-scan enforces this before DOM parsing, so a pathological deeply nested input is
rejected before it can grow parser state. The 65th open container receives `nesting_too_deep`.
Error precedence is `nesting_too_deep`, then `invalid_json`, then `duplicate_key`.

## Fixed Horizons and Holdouts

The CLI evaluates four fixed horizons:

| Label | Milliseconds |
|---|---:|
| `1m` | 60000 |
| `5m` | 300000 |
| `15m` | 900000 |
| `1h` | 3600000 |

The analyzer receives horizons as parameters rather than relying on scattered constants. This keeps
the evaluator ready for a later approved CLI configuration option without changing its methodology.

An origin becomes possible after at least three usable observations spanning ten seconds in one
session-local epoch. A holdout must be in that same epoch and within this tolerance of its horizon:

```text
min(declared sampling interval / 2, horizon / 10)
```

The forecast is projected to the holdout's actual elapsed time, not to the nominal horizon. A horizon
shorter than the declared sampling interval receives `horizon_below_sampling_interval`. A horizon
without a compatible observation receives `holdout_unavailable`.

## Shared Forecast Model

One lower-level memory-current forecast primitive is shared by `forecast evidence`, `trends`, and
forecast evaluation. It fits only observations available at the origin. A model projection is
clamped to zero and rounded to the nearest byte before every error calculation. A non-finite or
unrepresentable byte result receives `numeric_result_unavailable`.

Persistence is the paired baseline: it predicts the `memory.current` value observed at the origin.
Both methods use the same origins and holdouts.

## Sampling and Resource Limits

Origins are selected through deterministic streaming decimation. The first eligible origin is kept.
When more than 256 origins are retained, every second retained origin is removed and the stride is
doubled. The same retained origins are used for every horizon.

| Limit | Value | Purpose |
|---|---:|---|
| Active evaluation epochs | 1024 | Bounds simultaneous retained origin state. |
| Retained origins per epoch | 256 | Bounds rolling forecast state. |
| Result epochs | 4096 | Bounds total report aggregation. |
| Result rows | `result epochs × horizon count` | Currently at most 16384 rows. |

An epoch that is not eligible for forecasting produces one row with horizon `N/A`. An eligible epoch
produces one row for each horizon. Limits fail the complete report atomically; MemOptima does not
return a partial report. The error identifies the exceeded limit and advises splitting the manifest
or reducing the selected sessions.

## Metrics and Interpretation

An epoch and horizon requires at least three evaluated origins before it enters aggregate metrics.
The report aggregates epochs with equal weight and displays these per-horizon measures:

| Metric | Meaning |
|---|---|
| Mean epoch MAE | Typical absolute model error in bytes. |
| Mean epoch persistence MAE | Typical absolute error of the paired persistence baseline. |
| Mean epoch bias | Typical signed model error, predicted minus actual. |
| Mean epoch relative MAE | Typical error relative to origin memory in use. |
| Skill | Relative performance against persistence using AvgRelMAE. |

Relative MAE for one epoch and horizon is:

```text
sum(abs(model bytes - actual bytes)) / sum(max(origin current bytes, 1048576))
```

The one MiB denominator floor prevents tiny or empty containers from dominating the metric. It is
displayed as a percentage with two decimal places.

Skill is `1 - exp(mean(log(model MAE / persistence MAE)))` over contributing epochs. An epoch with
zero persistence error remains in the byte and relative-error metrics but not in skill. The report
separately counts `persistence_exact_model_exact` and `persistence_exact_model_error`. No
contributing epoch produces `N/A` skill. If no epoch contributes, skill is `N/A`. An epoch with
fewer than three evaluated origins has
`insufficient_origins` and contributes to none of the aggregate metrics.

These metrics evaluate memory-current projection only. They do not establish memory-limit risk,
time-to-limit accuracy, OOM likelihood, memory-leak diagnosis, anomaly diagnosis, or workload
safety.

## Deferred Work

Direct time-to-limit evaluation, headroom-normalized accuracy, configurable CLI horizons, confidence
intervals, JSON report output, anomaly detection, leak indicators, and recommendations are not part
of v0.10.0.
