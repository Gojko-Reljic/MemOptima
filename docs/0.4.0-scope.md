# MemOptima 0.4.0 Scope

## Purpose

MemOptima 0.4.0 adds bounded, on-demand collection of repeated Docker cgroup memory snapshots.
It creates an explicit local evidence artifact that can support later cause analysis and trend work
without claiming a trend or forecast in this release.

The release answers a narrow operational question:

```text
What did the supported Docker cgroup memory state and its assessment look like at each
explicitly requested sampling time?
```

Its role in the product control loop is:

```text
Observe → Assess → Retain bounded evidence → later: Forecast → Recommend → Act safely
```

## Release boundary

Version 0.4.0 is a Linux-only, local, on-demand, read-only CLI release. It reuses the rootful
Docker cgroup v2 discovery, cgroup memory snapshot reader, and assessment engine from 0.3.0. It
does not introduce a daemon, systemd service, database, network dependency, Docker socket access,
Docker CLI invocation by the product executable, or a system-changing action.

The release introduces one command:

```text
memoptima sample containers --count <COUNT> --interval <DURATION> --output <NEW_FILE>
```

All three options are required. The command accepts no short container ID and has no single-
container variant in this release.

| Option | Contract |
|---|---|
| `--count <COUNT>` | Required integer from `1` through `3600`, inclusive. It is the requested number of actual collection attempts. |
| `--interval <DURATION>` | Required duration from `100ms` through `60m`, inclusive. The accepted units are `ms`, `s`, and `m`; examples are `500ms`, `5s`, and `2m`. |
| `--output <NEW_FILE>` | Required path for a new JSON Lines evidence artifact. The path must not already exist. |

The command validates all options and the required cgroup v2 capabilities before it creates the
output file. An invalid option, existing output path, or unavailable required capability returns an
error and creates no artifact.

## Sampling schedule

The first collection attempt occurs immediately. Later attempts use a fixed-rate schedule derived
from a monotonic clock and the requested interval. This prevents system clock changes from changing
the intended cadence.

Each sample records a UTC capture time for users and a schedule-delay value for analysis. If a
collection takes longer than its interval, MemOptima does not start concurrent collection work. It
collects the next requested sample as soon as possible, records the delay, and preserves the
requested count as the number of actual collection attempts.

## Evidence artifact

### Creation, privacy, and durability

The command creates the output path exclusively. It never overwrites or appends to an existing
file. The created file has owner-only Linux permissions (`0600`). MemOptima does not create a
default history directory, database, or hidden persistent state.

Each completed JSON Lines record is written and flushed before the next collection attempt. Earlier
complete records therefore remain readable after a normal process interruption. Flushing does not
guarantee physical disk persistence across an abrupt power failure.

The artifact does not include hostname, user name, IP address, machine ID, or a derived host
identifier. It necessarily includes full Docker container IDs and discovered cgroup paths because
they identify the observed workload data.

### Record lifecycle

The first record has type `session_start`, followed by one `sample` record for each completed
collection attempt, followed by a terminal `session_end` record whenever MemOptima can write one.

`session_start` contains at least:

- a stable `schema_version`;
- the MemOptima application version;
- session start time in UTC;
- requested count and interval;
- the artifact privacy and durability contract.

Each `sample` record contains at least:

- its one-based sample sequence number;
- planned monotonic offset from the session start, actual UTC capture time, and schedule delay;
- structured discovery warnings for that collection;
- the complete list of currently discovered supported Docker containers.

An empty container list is a valid sample. It means no supported rootful Docker container was
discovered at that collection time; it is not a collection failure.

`session_end` contains the actual number of completed samples and one of these outcomes:

| Outcome | Meaning | Exit code |
|---|---|---:|
| `completed` | All requested samples were written. | `0` |
| `interrupted` | The user requested normal termination with `Ctrl+C`; completed samples remain valid. | `0` |
| `failed` | The requested session could not complete after artifact creation. | `1` |

If an output write or flush fails, MemOptima stops immediately, reports a clear standard-error
diagnostic, and returns `1`. If it cannot write `session_end`, the missing terminal record itself
marks the artifact as incomplete for a future reader.

The artifact has a fixed maximum size of 512 MiB. The writer reserves enough space for a terminal
failure record before starting another sample. Reaching the limit writes `session_end` with outcome
`failed`, reports the limit on standard error, and returns `1`.

### JSON value representation

The schema is versioned from its first release. Every expected raw cgroup metric has a stable field.

- Unsigned 64-bit byte values, event counters, PSI cumulative totals, and schedule durations are
  encoded as base-10 JSON strings to preserve full precision across JSON implementations.
- PSI percentage averages are JSON numbers because their domain is bounded from `0` through `100`.
- A metric that could not be read or validated is represented by `null` in its stable field, with a
  corresponding structured entry in `unavailable_metrics` containing its source, error code, and
  detail.
- A cgroup limit whose literal kernel value is `max` is represented by the string `"max"`; it is
  distinct from an unavailable `null` limit.

Each sampled container retains every metric already collected by the cgroup memory reader:

- current memory, `memory.high`, and `memory.max`;
- `memory.events` values;
- anonymous and file-backed memory composition;
- cgroup swap usage;
- complete cgroup memory PSI `some` and `full` values; and
- the current structured 0.3.0 assessment result, including risk, coverage, findings, evidence,
  recommendations, and unavailable evidence.

The raw snapshot is retained alongside the assessment so later versions can explain or re-evaluate
an assessment without inventing missing evidence.

## Partial data and diagnostics

An unavailable metric for one container does not stop a session or discard other available data.
Its raw snapshot and assessment preserve the partial state and structured reason. Discovery warnings
are retained in the matching sample record rather than repeatedly printed during collection.

Successful sampling is quiet while it runs. A terminal summary on standard error reports the final
outcome, completed sample count, and artifact path. Errors are written to standard error immediately.

## Safety and privacy boundary

MemOptima 0.4.0 does not:

- write to cgroup, procfs, sysfs, Docker, or host memory-management settings;
- access the Docker socket, Docker Engine API, or Docker CLI from the product executable;
- start a daemon, install a systemd service, or retain unrequested history;
- overwrite or append to an existing evidence artifact;
- infer a trend, predict an OOM event, diagnose a leak, or claim workload health;
- add automatic recommendations, approved actions, rollback, network transmission, a database, or
  a web dashboard.

## Test strategy

The normal Debug and Release suites must include deterministic coverage for:

- CLI parsing, required options, duration units, and every numeric boundary;
- existing output paths, exclusive creation, and owner-only output permissions;
- JSON Lines schema shape, stable field presence, large unsigned integer precision, unlimited limits,
  unavailable metrics, warnings, and empty container sets;
- `session_start`, completed samples, all terminal outcomes, and missing terminal records after an
  induced writer failure;
- fixed-rate monotonic scheduling, delay reporting, and interrupted sessions;
- partial container evidence without loss of other container data;
- 512 MiB artifact-limit enforcement without uncontrolled disk growth;
- preservation of raw cgroup data and assessment output in every sampled container.

The existing explicitly invoked Docker integration target must be extended to run a bounded sampling
session against one controlled rootful Docker container and validate its resulting artifact and
cleanup behavior.

## Acceptance criteria

MemOptima 0.4.0 is complete only when:

- `sample containers` has a documented, tested CLI contract;
- its artifact schema is versioned, documented, and tested for partial data and precision;
- it creates no output file before validation and capability checks succeed;
- it never overwrites an existing path and creates new artifacts with `0600` permissions;
- every completed sample is independently represented in a valid JSON Lines record;
- terminal outcomes distinguish completion, user interruption, and failure;
- it makes no trend, forecast, health, or action claim;
- Debug and Release suites, Release Valgrind, and the explicit Docker integration check pass under
  the project quality policy; and
- user-facing documentation explains the artifact, its privacy boundary, and its limitations.

## Planned evolution

A later release can add a reader for completed evidence artifacts and derive explainable trends only
from sufficient retained samples. A later history service, daemon, forecast, recommendation, or
action capability must remain opt-in, workload-scoped, explainable, rate-limited, auditable, and
reversible.
