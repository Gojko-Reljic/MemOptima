# MemOptima 0.3.0 Scope

## Purpose

MemOptima 0.3.0 adds a transparent, read-only assessment layer on top of the Docker cgroup v2
observability foundation delivered in 0.2.0.

The release answers a narrow operational question:

```text
Which currently observable cgroup memory-boundary and OOM signals require attention,
and what evidence supports that conclusion?
```

It does not predict future behavior, infer trends from a single snapshot, or modify a workload or
host. Its role in the product control loop is:

```text
Observe → Assess → later: Forecast → Recommend → Act safely
```

## Release boundary

Version 0.3.0 is a Linux-only, local, on-demand, read-only CLI release. It reuses the 0.2.0
rootful Docker cgroup v2 discovery and memory snapshot reader without adding Docker socket, Docker
CLI, daemon, database, or network dependencies to the `memoptima` executable.

The release introduces a separate analysis command group:

| Command | Purpose |
|---|---|
| `memoptima assess containers` | Lists every discovered supported Docker container with an assessment summary. |
| `memoptima assess container <FULL_ID>` | Displays the complete assessment for one discovered supported Docker container. |

`<FULL_ID>` accepts only a 64-character hexadecimal Docker container ID. Uppercase hexadecimal
characters are normalized. Short prefixes are not supported.

The 0.2.0 `containers` and `container <FULL_ID>` commands remain raw observability commands. Their
contracts do not gain risk conclusions in this release.

## Assessment result model

An assessment contains:

- an overall risk level: `Low`, `Moderate`, `High`, or `Critical`;
- an assessment coverage value: `Complete` or `Partial`;
- zero or more structured findings;
- unavailable evidence explaining any partial coverage.

The overall risk is the highest risk level among all findings. If no finding is produced, the
overall risk is `Low`. `Low` means that this release found no currently observable boundary or OOM
signal; it does not assert that the workload is healthy or that future risk is absent.

Each finding has a stable code, risk level, evidence, and a fixed safe recommendation. Findings are
sorted from the highest risk to the lowest risk, with the stable finding code as a tie-breaker.

## Coverage and uncertainty

Every rule evaluates only independently available evidence. A missing or invalid metric does not
discard findings supported by other metrics.

When a metric required by one or more rules is unavailable, the assessment coverage is `Partial`.
The detailed command lists the unavailable evidence and its reader-provided reason. The summary
command exposes coverage in a dedicated column.

`Risk` represents the highest demonstrated risk, not an estimate that unavailable data is safe.

## Rule catalog

All rules operate on one point-in-time `CgroupMemorySnapshot`. Event counters are cumulative since
the cgroup was created; their nonzero values are historical evidence, not proof of a recent increase.

| Code | Condition | Risk | Safe recommendation |
|---|---|---|---|
| `memory_max_utilization_moderate` | A finite `memory.max` exists and `90% <= memory.current / memory.max < 98%`. | Moderate | Review workload demand and the configured `memory.max` before hard-limit pressure develops. |
| `memory_max_utilization_high` | A finite `memory.max` exists and `98% <= memory.current / memory.max <= 100%`. | High | Review workload demand and the configured `memory.max` before a cgroup OOM condition occurs. |
| `memory_max_exceeded` | A finite `memory.max` exists and `memory.current > memory.max`. | Critical | Treat this as incident data; inspect the workload and cgroup configuration before applying any change. |
| `memory_high_reached` | A finite `memory.high` exists and either `memory.current >= memory.high` or `memory.events.high > 0`. | Moderate | Review `memory.high` and the workload working set before pressure reaches `memory.max`. |
| `memory_max_event_recorded` | `memory.events.max > 0`. | High | Investigate hard-limit pressure and review `memory.max` with the workload's memory demand. |
| `oom_event_recorded` | `memory.events.oom > 0`. | High | Investigate cgroup OOM conditions and application logs before retrying or resizing the workload. |
| `oom_kill_recorded` | `memory.events.oom_kill > 0`. | Critical | Treat this as a workload incident; inspect process recovery and cgroup memory settings. |

The literal cgroup value `max` is unlimited. It does not participate in the percentage-based
`memory.max` or `memory.high` rules.

## Command behavior

### `memoptima assess containers`

The command first performs the same cgroup v2 capability checks and Docker discovery as
`memoptima containers`. It then assesses every discovered container and prints a deterministic
summary table:

```text
CONTAINER ID    RISK    COVERAGE    TOP FINDING    FINDINGS
```

Rows are sorted by full container ID. `TOP FINDING` is the first finding after the defined finding
sort order. For `Low` risk without findings, it is displayed as `None` and the finding count is `0`.

Discovery warnings remain on standard error. A successful assessment returns exit code `0`, even
when discovery warnings exist or assessment coverage is partial. Capability failures return exit
code `1`.

### `memoptima assess container <FULL_ID>`

The command validates the full ID, discovers supported Docker cgroups, and assesses the matching
container. It prints:

```text
Container
Overall risk
Coverage
Findings
Unavailable evidence
```

Every finding includes its code, risk, evidence, and fixed recommendation. The command does not
repeat the complete raw cgroup snapshot; `memoptima container <FULL_ID>` remains the raw data
command.

An invalid or missing ID is a usage error with exit code `2`. A valid but undiscovered ID and any
host capability failure return exit code `1`.

## Safety and privacy boundary

MemOptima 0.3.0 does not:

- write to cgroup, procfs, sysfs, Docker, or host memory-management settings;
- access the Docker socket, Docker Engine API, or Docker CLI from the product executable;
- start a daemon, retain history, create a database, or transmit data over the network;
- use universal PSI thresholds, anon/file ratios, or swap ratios as risk rules;
- infer a trend, predict an OOM event, diagnose a leak, or claim workload health from one snapshot;
- apply, propose for automatic approval, or roll back any action.

## Test strategy

The normal Debug and Release suites must contain deterministic tests for:

- risk-level ordering and overall-risk aggregation;
- every rule boundary, including 90%, 98%, 100%, and a value above `memory.max`;
- `max` limits, unavailable metrics, and `Complete` versus `Partial` coverage;
- cumulative event evidence without a recency claim;
- finding codes, evidence, recommendations, and stable sort order;
- assessment summary and detailed formatting;
- CLI usage errors, capability failures, empty discovery, and unknown container IDs.

The explicitly invoked Docker integration target verifies raw discovery and both assessment commands
against one controlled rootful Docker cgroup. It remains outside the normal test suite because it
requires a reachable Docker daemon and creates then removes one uniquely named, labeled test
container.

## Acceptance criteria

MemOptima 0.3.0 is complete only when:

- both assessment commands have documented and tested CLI contracts;
- every rule in this document has deterministic boundary coverage;
- no assessment result makes an unsupported trend, prediction, health, or recency claim;
- partial evidence is explicit in both the model and CLI output;
- the 0.2.0 raw observability commands retain their documented behavior and test coverage;
- Debug and Release suites pass under the project quality policy;
- user-facing documentation explains the assessment scope and safety boundary.

## Planned evolution

Later releases can introduce repeated sampling and retained evidence before adding forecasts. Any
future recommendation or action capability must remain workload-scoped, explainable, explicitly
approved, rate-limited, auditable, and reversible.
