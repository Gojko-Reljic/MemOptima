# MemOptima 0.7.0 Scope

## Purpose

MemOptima 0.7.0 adds local, read-only cross-session analysis of Docker container memory evidence.
It evaluates explicitly selected schema-version-1 artifacts and reports `memory.current` behavior
for each compatible container observation epoch.

It does not diagnose memory leaks, predict OOM events, or modify hosts, containers, or cgroups.

## Public command

```text
memoptima trend manifest <FILE>
memoptima trend manifest <FILE> --format json
```

The default output is a table. `--format json` selects the versioned JSON report.

| Exit code | Meaning |
|---:|---|
| `0` | A valid report was produced, including one with no rate-eligible epochs. |
| `1` | An input/runtime failure or resource limit occurred. |
| `2` | The command usage is invalid. |

## Input boundary

The command accepts one explicit manifest, not a directory scan, daemon configuration, or database
query. It processes at most 128 artifacts and 4,096 active container observation epochs through
streaming input. Exceeding a resource limit fails the command rather than producing a partial report.

Every selected artifact must be readable, safe, schema-version-1-valid, and lifecycle-valid. One
invalid artifact fails the entire report.

## Observation epochs

One result represents one Docker container observation epoch. An epoch requires the same full Docker
container ID and cgroup path throughout compatible observations.

An epoch ends when its identity changes, timestamps are not strictly increasing, `memory.current` is
unavailable, or `memory.max` changes. A container absent from a session is an explicit observation
gap. If the same strict identity appears later, it remains part of the same epoch, but its quality can
become `sparse`. Overlapping sessions for the same strict identity are ambiguous input.

## Trend and limit rules

Version 0.7.0 calculates only a numeric `memory.current` rate. It requires at least three
observations across at least ten seconds with strictly increasing timestamps.

`memory.max` supplies limit context. A current-memory rate can remain available when `memory.max` is
unlimited or unavailable. A time-to-limit estimate requires continuous quality, a stable finite limit,
an available current-memory rate, and the existing v0.6 conservative limit-crossing conditions.

A gap is `sparse` when it exceeds twice the larger adjacent declared sampling interval. Sparse
evidence may retain a long-term current-memory rate, but cannot provide a time-to-limit estimate.

## Output and non-goals

The table abbreviates container IDs. JSON retains full Docker IDs and cgroup paths for local audit.
Neither output labels a workload as stable, rising, falling, anomalous, risky, or leaking.

Version 0.7.0 does not add a daemon, database, dashboard, alerting, directory scan, PSI/swap/cache
trend model, leak diagnosis, OOM prediction, risk score, automatic recommendation, automatic action,
or logical workload identity across redeployments.
