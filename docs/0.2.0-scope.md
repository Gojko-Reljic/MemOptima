# MemOptima 0.2.0 Scope

## Purpose

MemOptima 0.2.0 extends the completed host-level MVP with a read-only, Docker-aware cgroup v2 observability layer.

The release does not attempt to replace the Linux memory manager, Docker, or Kubernetes resource management. Its purpose is to show the memory state of individual Docker workloads with the Linux signals needed for later diagnosis, forecasting, and carefully controlled remediation.

The production objective is to make the following distinction observable and explainable:

```text
A workload is approaching its own cgroup memory limit
    is different from
The host as a whole is running out of memory.
```

This distinction is important because a container can be OOM-killed by its cgroup limit while the host still has available memory.

## Release boundary

Version 0.2.0 is an on-demand, local, read-only CLI release. It adds Docker container snapshots but does not change the behavior of the existing `status`, `processes`, or `monitor` commands.

The release introduces these commands:

| Command | Purpose |
|---|---|
| `memoptima containers` | Lists discovered supported Docker containers and a compact memory-pressure summary. |
| `memoptima container <id>` | Displays the complete available cgroup memory snapshot for one Docker container. |

`<id>` accepts either:

- the full 64-character hexadecimal Docker container ID; or
- a unique hexadecimal prefix containing at least 12 characters.

MemOptima rejects an unknown or ambiguous prefix. It never guesses which container the user intended.

## Supported environment

The 0.2.0 production baseline is a Linux host with kernel version 5.10 or newer. Runtime capability checks, rather than the kernel version alone, are the authority for whether the commands can run.

The commands require all of the following:

- a unified cgroup v2 hierarchy;
- an available cgroup v2 `memory` controller;
- the cgroup memory files required by this release;
- host and per-cgroup Linux PSI memory interfaces;
- rootful Docker Engine containers using either supported cgroup v2 layout.

The supported rootful Docker Engine layouts are:

| Docker cgroup driver | Expected cgroup v2 container layout |
|---|---|
| `systemd` | `/sys/fs/cgroup/system.slice/docker-<full-container-id>.scope/` |
| `cgroupfs` | `/sys/fs/cgroup/docker/<full-container-id>/` |

Rootless Docker, Kubernetes workload discovery, containerd-only discovery, and cgroup v1 are outside the scope of this release.

## Data collection

For every discovered supported Docker cgroup, MemOptima reads and validates the following local cgroup v2 data.

| Source | Values | Why it is collected |
|---|---|---|
| `memory.current` | Current memory usage in bytes. | Identifies the workload's current cgroup memory footprint. |
| `memory.high` | Reclaim and throttling boundary, or `max`. | Shows whether a soft memory boundary is configured. |
| `memory.max` | Hard memory boundary, or `max`. | Shows the limit that can result in a cgroup OOM condition. |
| `memory.events` | `high`, `max`, `oom`, and `oom_kill` counters. | Supplies evidence that the workload crossed a boundary or experienced a cgroup OOM event. |
| `memory.stat` | `anon` and `file` byte values. | Separates anonymous-memory growth from file-backed or page-cache growth. |
| `memory.swap.current` | Current cgroup swap usage in bytes. | Shows whether this workload is using swap. |
| `memory.pressure` | `some` and `full` PSI values for 10, 60, and 300 second windows, plus cumulative totals. | Measures time that the workload stalls because of memory pressure. |

`memory.high` and `memory.max` can contain the literal `max`. MemOptima represents that value as an unlimited boundary, not as a numeric zero.

`memory.stat` values are evidence, not exact private ownership accounting. In particular, file-backed memory can include reclaimable cache and shared pages. MemOptima 0.2.0 does not diagnose a memory leak or cache misconfiguration from one snapshot.

## PSI presentation

Linux PSI exposes two memory-pressure categories:

- `some`: at least one task in the cgroup is stalled for memory;
- `full`: all non-idle tasks in the cgroup are stalled for memory at the same time.

The summary command displays the short-term `some avg10` and `full avg10` percentages. These values are compact enough for a multi-container table and most relevant to a current snapshot.

The detailed command exposes all collected PSI windows and cumulative totals. The internal model validates and retains all of them so a later history or forecasting feature does not require replacing the collector.

PSI values in 0.2.0 are observations. The release does not attach a universal risk threshold or recommendation to a PSI percentage.

## Command behavior

### `memoptima containers`

The command discovers supported rootful Docker cgroups, reads their available data, and prints a compact table. Containers are ordered by `memory.current` in descending order. A full container ID in ascending order breaks ties, so the result is deterministic for users and tests.

The table includes, at minimum:

```text
CONTAINER ID    CURRENT     HIGH        MAX         PSI SOME  PSI FULL  OOM KILLS
```

Container IDs are shortened for readability in the table. The detailed command accepts the shown 12-character ID when it is unique.

When no supported Docker containers are found, the command succeeds and explains that no supported rootful Docker cgroups were discovered. An empty workload set is not a runtime failure.

### `memoptima container <id>`

The command resolves the supplied full ID or unique prefix and prints a complete per-container snapshot. It includes:

- full container ID;
- cgroup path;
- current, high, and maximum memory values;
- anonymous and file-backed memory values;
- current swap usage;
- all required `memory.events` counters;
- all collected PSI averages and cumulative totals;
- explicit notes for unavailable individual metrics.

The command does not make a recommendation, apply a policy, modify a cgroup file, or contact Docker.

## Capability checks and partial results

MemOptima validates host-level prerequisites before it attempts Docker discovery. A missing unified cgroup v2 hierarchy, unavailable memory controller, or unavailable required PSI interface produces a clear diagnostic on standard error and exit code `1`.

After the host prerequisites pass, an individual container can still be unreadable because of file permissions, process lifetime changes, or an incomplete controller interface. In that case MemOptima:

1. preserves every independently readable metric for that container;
2. represents the unavailable metric as `N/A` in detailed output;
3. reports an explicit warning; and
4. continues processing other discovered containers.

A single unreadable workload must not hide the state of every other workload.

## Safety and privacy boundary

MemOptima 0.2.0 is intentionally least-privilege and read-only.

It does not:

- require `sudo`, root execution, Docker group membership, or access to `/var/run/docker.sock`;
- invoke the Docker CLI or Docker Engine API;
- create, start, stop, pause, kill, resize, or otherwise control a container;
- write to a cgroup v2 control file;
- change `memory.high`, `memory.max`, `memory.low`, swap configuration, or host `vm.*` settings;
- start a daemon, install a systemd service, create a database, or persist monitoring history;
- transmit runtime data over the network.

Docker socket access is deliberately excluded. Although it would provide container names and image metadata, it grants much broader Docker daemon authority than a read-only collector requires. Container IDs and cgroup filesystem data are sufficient for this release.

## Test strategy

Every normal build and test run must include deterministic fixture-based tests for:

- cgroup v2 capability detection;
- both supported Docker cgroup path layouts;
- parsing valid and malformed memory controller data;
- `max` versus numeric boundary handling;
- PSI parsing and validation;
- full ID and unique-prefix resolution, including ambiguous and unknown IDs;
- deterministic container sorting;
- table and detailed-output formatting;
- empty, partial, and unsupported-host outcomes.

MemOptima also provides a separate, explicitly invoked Docker integration target. It runs only on a suitable Linux host with rootful Docker, cgroup v2, and the required readable controller files. This separates reproducible unit testing from real-environment verification.

## Acceptance criteria

MemOptima 0.2.0 is complete only when all of the following are true:

- `containers` and `container <id>` have documented, tested CLI contracts;
- both rootful Docker cgroup v2 driver layouts are covered by fixtures;
- host capability failures and individual-container partial failures are distinguishable and tested;
- no supported command writes to Docker, cgroup, procfs, sysfs, or local persistence;
- the existing 0.1.0 commands retain their behavior and test coverage;
- Debug and Release test suites pass under the established project quality policy;
- the optional real Docker integration target has a documented execution method and expected result;
- user-facing documentation explains all support boundaries and privilege expectations.

## Explicit non-goals

The following remain outside 0.2.0:

- Docker names, images, labels, and Compose service metadata;
- rootless Docker support;
- Kubernetes discovery, a Kubernetes controller, CRDs, or direct Kubernetes API access;
- continuous container monitoring, a daemon, stored history, incident snapshots, or a web dashboard;
- memory-leak detection, risk forecasting, universal PSI thresholds, or automatic recommendations;
- cgroup changes, memory reclaim, automatic remediation, rollback, or audit logging;
- eBPF collection, `userfaultfd`, custom page replacement, kernel modules, or host-global memory tuning.

## Planned evolution

Later versions can build the production control loop on top of this release:

```text
0.2.0  Observe Docker cgroup v2 and PSI state
   ↓
Later  Explain causes and classify workload risk
   ↓
Later  Forecast risk from retained evidence and trends
   ↓
Later  Recommend the smallest safe action
   ↓
Later  Apply explicitly approved, reversible workload-local actions
   ↓
Later  Verify the result, retain an audit trail, and roll back when needed
```

Each later system-changing capability must remain opt-in, workload-scoped, explainable, rate-limited, auditable, and reversible.
