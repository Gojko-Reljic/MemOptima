# MemOptima v0.7 Trend Analyzer Design

## Purpose

This document specifies the domain analyzer that derives cross-session `memory.current` trends from
validated local evidence. It is a design contract for implementation and tests; it does not add a
new command, change schema-v1 evidence, or authorize an automatic system action.

## Boundary and data flow

```text
Trend manifest
    -> validated session catalog
    -> typed evidence replay adapter
    -> session-aware trend analyzer
    -> trend epoch results
    -> future table and JSON presenters
```

The replay adapter owns artifact paths and the internal typed evidence reader. The analyzer owns no
filesystem, JSON, Docker, or terminal dependency. Its inputs are already validated typed values;
its outputs are deterministic domain results.

## Public C++ API contract

The implementation introduces a public header named
`include/memoptima/trends/trend_analyzer.hpp`. Its types are plain aggregates and `enum class`
values. The analyzer uses C++ domain types, never canonical timestamp strings; presentation converts
timestamps only after analysis is complete.

```cpp
using TrendTimePoint = std::chrono::sys_time<std::chrono::milliseconds>;

enum class TrendMemoryMaximumKind {
    finite,
    unlimited,
    unavailable,
};

struct TrendMemoryMaximum {
    TrendMemoryMaximumKind kind;
    std::uint64_t bytes{};
};

struct TrendSessionStart {
    TrendTimePoint started_at;
    std::uint64_t requested_interval_ms;
};

struct TrendSampleStart {
    TrendTimePoint captured_at;
};

struct TrendObservation {
    TrendContainerIdentity identity;
    std::optional<std::uint64_t> current_memory_bytes;
    TrendMemoryMaximum maximum_memory;
};

struct TrendSessionEnd {
    bool incomplete;
};
```

`TrendContainerIdentity` is the existing public pair of the full Docker container ID and cgroup
path. `TrendMemoryMaximum.bytes` is meaningful only for `finite`; a zero-byte finite maximum is
valid. The `unlimited` and `unavailable` states require `bytes == 0`. Any other combination is an
analyzer input error.

The stateful analyzer has this event-oriented shape:

```cpp
class TrendAnalyzer {
  public:
    [[nodiscard]] std::expected<void, TrendAnalyzerError>
    begin_session(const TrendSessionStart &start);

    [[nodiscard]] std::expected<void, TrendAnalyzerError>
    begin_sample(const TrendSampleStart &sample);

    [[nodiscard]] std::expected<void, TrendAnalyzerError>
    observe(const TrendObservation &observation);

    [[nodiscard]] std::expected<void, TrendAnalyzerError> end_sample();

    [[nodiscard]] std::expected<void, TrendAnalyzerError>
    end_session(const TrendSessionEnd &end);

    [[nodiscard]] std::expected<TrendAnalysis, TrendAnalyzerError> finish();
};
```

Events must occur in the documented nested order. `finish()` is valid only when no session or sample
is open. The analyzer is single use after a successful `finish()`; another event or `finish()` call
returns `invalid_event_sequence`, and a new analysis requires a new analyzer instance. The public
interface does not accept artifact paths, JSON values, line numbers, Docker discovery data, or CLI
options.

```cpp
enum class TrendAnalyzerErrorCode {
    invalid_event_sequence,
    duplicate_observation,
    invalid_observation,
    resource_limit_exceeded,
};

struct TrendAnalyzerError {
    TrendAnalyzerErrorCode code;
    std::string detail;
};
```

`invalid_event_sequence` covers nesting violations and finishing with an open event. A duplicate
strict identity in one sample is `duplicate_observation`. A noncanonical maximum-memory value is
`invalid_observation`. Reaching either the active-epoch or total-result bound is
`resource_limit_exceeded`. Missing metrics, sparse gaps, non-positive growth, and incomplete
sessions are valid analytical outcomes, not errors.

Each sample accepts up to 4,096 distinct strict identities. Accepted observations count toward this
budget even when current memory is unavailable. At capacity, an otherwise valid observation of an
existing identity returns `duplicate_observation`. An otherwise valid observation of a new identity
returns `resource_limit_exceeded` and leaves sample membership intact. The budget resets for each
sample.

## Streaming input contract

The analyzer receives ordered events for every cataloged evidence artifact:

1. `begin_session` supplies a session start time and its declared sampling interval. Event order
   defines session order; artifact identity remains in the replay adapter.
2. `begin_sample` supplies a sample capture time.
3. `observe` supplies a strict container identity, optional current memory, and the state of its
   maximum memory limit.
4. `end_sample` closes the sample membership set.
5. `end_session` supplies session completion information.

A strict container identity is the pair of a full Docker container ID and cgroup path. A container
that is active but not observed before `end_sample` is recorded as an observation gap; it is never
treated as silently continuous.

Each observation represents metrics as follows:

| Metric | Representation | Analyzer effect |
| --- | --- | --- |
| `memory.current` | available bytes or unavailable | Unavailable closes the active epoch. |
| `memory.max` | finite bytes, unlimited, or unavailable | Unlimited and unavailable preserve the usage trend but prevent time-to-limit. |
| sampling interval | unsigned milliseconds from session start | Used with neighboring observations to evaluate gaps. |

## Epoch lifecycle

An epoch contains comparable observations for one strict identity. It begins with an available
`memory.current` observation and ends before any incompatible observation. The analyzer creates a
new epoch when comparable data later resumes.

The following conditions close an epoch:

- unavailable `memory.current`;
- any semantic transition of `memory.max` between finite, unlimited, or unavailable, including a
  changed finite value;
- a non-increasing timestamp for the same identity.

For an observation with available current memory, a non-increasing timestamp closes the preceding
epoch with `non_increasing_timestamp`, even if the maximum also changes. That observation starts the
next epoch in input order. An active identity absent at `end_sample` stays active and retains its last
observation. When it reappears in the same epoch, the gap runs between the two actual observations.
The gap is sparse only when it exceeds twice the larger of their declared sampling intervals.

An incomplete session marks every epoch to which it contributed an observation with available
current memory, including epochs that closed before `end_session`.

The analyzer accepts at most 4,096 active epochs and 4,096 total epochs, including closed epochs.
A new epoch consumes one result slot when it begins. If `observe()` would exceed either limit, it
returns `resource_limit_exceeded` before changing sample membership or epoch state.

## Rate calculation

An epoch has an available current-memory rate only when it contains at least three observations over
at least ten seconds with strictly increasing timestamps and available `memory.current` values.

The rate is the ordinary least-squares slope of memory bytes against elapsed seconds. Each timestamp
is converted to an offset from the epoch's first timestamp before calculation. This avoids loss of
numeric precision from large absolute UTC timestamps. The signed result is reported in bytes per
second; negative and zero values are valid measurements and do not receive direction or risk labels.

## Time-to-limit eligibility

Time to `memory.max` is an estimate of a finite configured limit crossing, never an OOM prediction.
It is available only when all of the following are true:

- the epoch has continuous evidence;
- `memory.max` is stable and finite;
- the current-memory rate is available and positive;
- the latest observed current memory is below the finite maximum.

If the latest current memory is at or above its finite maximum, the result reports
`already_at_or_above_maximum` instead of inventing a future duration.

The estimate is calculated from the latest actual observation, not from a fitted value at that
timestamp:

```text
estimated_duration_ms = floor((finite_maximum_bytes - latest_current_bytes) /
                              growth_bytes_per_second * 1000)
```

`estimated_duration_ms` is a `std::uint64_t` whole-millisecond count. Rounding down avoids
displaying more remaining time than the model calculated. A value of `0` means the model's positive
estimate is shorter than one millisecond; it is distinct from `already_at_or_above_maximum`. If the
positive mathematical result is non-finite or exceeds `std::uint64_t` after rounding, the analyzer
reports `duration_out_of_range` and does not emit a duration value.

For example, observations of `0 B`, `100 B`, and `100 B` at `0 s`, `10 s`, and `20 s` have an
ordinary least-squares growth rate of `5 B/s`. With a `200 B` finite maximum, the latest actual
value is `100 B`, so the estimate is `(200 - 100) / 5 = 20 s`, or `20,000 ms`.

## Result statuses

The domain result uses stable enum values, not presentation text. Table and JSON layers map these
values to their respective public formats.

```cpp
enum class TrendRateStatus {
    available,
    insufficient_observations,
    insufficient_duration,
};

enum class TrendTimeToLimitStatus {
    available,
    rate_unavailable,
    non_positive_growth,
    sparse_evidence,
    unlimited_maximum,
    unavailable_maximum,
    already_at_or_above_maximum,
    duration_out_of_range,
};
```

`TrendRateStatus`:

- `available`
- `insufficient_observations`
- `insufficient_duration`

`TrendTimeToLimitStatus`:

- `available`
- `rate_unavailable`
- `non_positive_growth`
- `sparse_evidence`
- `unlimited_maximum`
- `unavailable_maximum`
- `already_at_or_above_maximum`
- `duration_out_of_range`

```cpp
enum class TrendEvidenceQuality {
    continuous,
    sparse,
};

enum class TrendContinuityBreakReason {
    current_memory_unavailable,
    memory_maximum_changed,
    non_increasing_timestamp,
};

struct TrendCurrentMemoryResult {
    std::uint64_t first_bytes;
    std::uint64_t last_bytes;
    TrendRateStatus rate_status;
    std::optional<double> growth_bytes_per_second;
};

struct TrendTimeToLimitResult {
    TrendTimeToLimitStatus status;
    std::optional<std::uint64_t> estimated_duration_ms;
};

struct TrendEpochResult {
    TrendContainerIdentity identity;
    std::uint32_t epoch_index;
    TrendTimePoint first_observed_at;
    TrendTimePoint last_observed_at;
    std::uint64_t observation_count;
    std::uint64_t observation_window_ms;
    std::uint64_t largest_gap_ms;
    TrendEvidenceQuality quality;
    bool contains_incomplete_session;
    std::optional<TrendContinuityBreakReason> termination_reason;
    TrendCurrentMemoryResult current_memory;
    TrendMemoryMaximum maximum_memory;
    TrendTimeToLimitResult time_to_limit;
};

struct TrendAnalysisSummary {
    std::uint64_t epoch_count;
    std::uint64_t continuous_epoch_count;
    std::uint64_t sparse_epoch_count;
    std::uint64_t incomplete_epoch_count;
    std::uint64_t rate_available_epoch_count;
    std::uint64_t time_to_limit_available_epoch_count;
};

struct TrendAnalysis {
    TrendAnalysisSummary summary;
    std::vector<TrendEpochResult> epochs;
};
```

Every epoch result also retains its observation count, UTC time endpoints, observed window, largest
gap, evidence quality, maximum-memory context, and continuity-break information. It carries the full
Docker ID and cgroup path; presentation may abbreviate the ID only in terminal tables.

`TrendAnalyzer` returns no more than 4,096 total epoch results. Epoch indices start at 1 within each
strict identity and follow the order in which those epochs opened. The `epochs` vector is ordered by
full Docker container ID, cgroup path, and then `epoch_index`, all ascending. The analyzer computes
the summary. Manifest metadata, artifact paths, JSON result versioning, and presentation text belong
to later application and presentation layers.

Exactly one time-to-limit status is primary. When more than one condition applies, the analyzer uses
this precedence order:

1. `already_at_or_above_maximum`
2. `unlimited_maximum`
3. `unavailable_maximum`
4. `sparse_evidence`
5. `rate_unavailable`
6. `non_positive_growth`
7. `duration_out_of_range`
8. `available`

The epoch's separate quality and maximum-context fields preserve lower-priority facts. For example,
an epoch with sparse evidence and an unlimited maximum reports `unlimited_maximum` as its primary
time-to-limit status while still reporting `sparse` quality.

## Required test matrix

The pure analyzer test suite must cover at least:

- a continuous finite-limit epoch with a positive regression rate and available time-to-limit;
- a valid negative or zero rate with no time-to-limit estimate;
- fewer than three observations and a window shorter than ten seconds;
- unlimited and unavailable maximums preserving the rate but preventing time-to-limit;
- a changed finite maximum closing an epoch;
- unavailable current memory closing an epoch;
- an absent container producing a sparse gap after it reappears;
- a gap exactly at, and one millisecond above, the sparse threshold;
- observations at `20 s` and `40 s` with a missing `30 s` sample and a declared `10 s` interval:
  the `20 s` gap equals, but does not exceed, the `20 s` sparse threshold, so quality remains
  continuous and time-to-limit remains eligible when all other conditions hold;
- a non-increasing timestamp producing an explicit continuity break without reordering input;
- independent epochs for distinct cgroup paths or container IDs;
- the `0 B`, `100 B`, `100 B` at `0 s`, `10 s`, `20 s` example with a `200 B` maximum, asserting a
  `5 B/s` regression rate and a `20,000 ms` estimate;
- a `1 TiB` finite maximum with `0 B`, `0 B`, `1 B` at `0 s`, `10 s`, `20 s`, asserting the
  `0.05 B/s` regression rate and the representable `21,990,232,555,500,000 ms` estimate;
- a positive finite estimate that exceeds `std::uint64_t`, asserting `duration_out_of_range` and no
  duration value;
- status precedence for overlapping conditions, including sparse evidence with unlimited or
  unavailable maximums, sparse evidence with an unavailable rate, and a finite maximum already
  reached despite sparse evidence;
- bounded active-epoch behavior and deterministic result ordering;
- acceptance of 4,096 distinct identities per sample, rejection of the next new identity, duplicate
  detection at capacity, and a fresh budget in the next sample.

## Safety and non-goals

v0.7 reports measurements, eligibility, and quality only. It does not claim an OOM prediction,
confirmed memory leak, anomaly, workload diagnosis, safe remediation, or automatic action. PSI,
swap, cache, recommendations, backtesting, calibrated classifications, alerts, services, and a
dashboard remain outside this analyzer's scope.
