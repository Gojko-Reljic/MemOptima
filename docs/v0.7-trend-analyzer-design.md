# MemOptima v0.7 Trend Analyzer Design

## Purpose

This document specifies the domain analyzer that derives cross-session `memory.current` trends from
validated local evidence. It is a design contract for implementation and tests; it does not add a
new command, change schema-v1 evidence, or authorize an automatic system action.

## Boundary and data flow

```text
Trend manifest
    -> validated session catalog
    -> typed evidence replay adapter
    -> session-aware trend analyzer
    -> trend epoch results
    -> future table and JSON presenters
```

The replay adapter owns artifact paths and the internal typed evidence reader. The analyzer owns no
filesystem, JSON, Docker, or terminal dependency. Its inputs are already validated typed values;
its outputs are deterministic domain results.

## Streaming input contract

The analyzer receives ordered events for every cataloged evidence artifact:

1. `begin_session` supplies a session identity, its start time, and its declared sampling interval.
2. `begin_sample` supplies a sample capture time.
3. `observe` supplies a strict container identity, optional current memory, and the state of its
   maximum memory limit.
4. `end_sample` closes the sample membership set.
5. `end_session` supplies session completion information.

A strict container identity is the pair of a full Docker container ID and cgroup path. A container
that is active but not observed before `end_sample` is recorded as an observation gap; it is never
treated as silently continuous.

Each observation represents metrics as follows:

| Metric | Representation | Analyzer effect |
| --- | --- | --- |
| `memory.current` | available bytes or unavailable | Unavailable closes the active epoch. |
| `memory.max` | finite bytes, unlimited, or unavailable | Unlimited and unavailable preserve the usage trend but prevent time-to-limit. |
| sampling interval | unsigned milliseconds from session start | Used with neighboring observations to evaluate gaps. |

## Epoch lifecycle

An epoch contains comparable observations for one strict identity. It begins with an available
`memory.current` observation and ends before any incompatible observation. The analyzer creates a
new epoch when comparable data later resumes.

The following conditions close an epoch:

- unavailable `memory.current`;
- any semantic transition of `memory.max` between finite, unlimited, or unavailable, including a
  changed finite value;
- a non-increasing timestamp for the same identity.

The analyzer records `non_increasing_timestamp` as an explicit continuity-break reason. It must not
sort or otherwise repair input ordering. At each `end_sample`, an active identity absent from that
sample creates a gap rather than an immediate epoch boundary. A gap is sparse only when it exceeds
twice the larger of the two adjacent declared sampling intervals.

## Rate calculation

An epoch has an available current-memory rate only when it contains at least three observations over
at least ten seconds with strictly increasing timestamps and available `memory.current` values.

The rate is the ordinary least-squares slope of memory bytes against elapsed seconds. Each timestamp
is converted to an offset from the epoch's first timestamp before calculation. This avoids loss of
numeric precision from large absolute UTC timestamps. The signed result is reported in bytes per
second; negative and zero values are valid measurements and do not receive direction or risk labels.

## Time-to-limit eligibility

Time to `memory.max` is an estimate of a finite configured limit crossing, never an OOM prediction.
It is available only when all of the following are true:

- the epoch has continuous evidence;
- `memory.max` is stable and finite;
- the current-memory rate is available and positive;
- the latest observed current memory is below the finite maximum.

If the latest current memory is at or above its finite maximum, the result reports
`already_at_or_above_maximum` instead of inventing a future duration.

## Result statuses

The domain result uses stable enum values, not presentation text. Table and JSON layers map these
values to their respective public formats.

`TrendRateStatus`:

- `available`
- `insufficient_observations`
- `insufficient_duration`

`TrendTimeToLimitStatus`:

- `available`
- `rate_unavailable`
- `non_positive_growth`
- `sparse_evidence`
- `unlimited_maximum`
- `unavailable_maximum`
- `already_at_or_above_maximum`

Every epoch result also retains its observation count, canonical UTC endpoints, observed window,
largest gap, evidence quality, maximum-memory context, and continuity-break information. It carries
the full Docker ID and cgroup path; presentation may abbreviate the ID only in terminal tables.

## Required test matrix

The pure analyzer test suite must cover at least:

- a continuous finite-limit epoch with a positive regression rate and available time-to-limit;
- a valid negative or zero rate with no time-to-limit estimate;
- fewer than three observations and a window shorter than ten seconds;
- unlimited and unavailable maximums preserving the rate but preventing time-to-limit;
- a changed finite maximum closing an epoch;
- unavailable current memory closing an epoch;
- an absent container producing a sparse gap after it reappears;
- a gap exactly at, and one millisecond above, the sparse threshold;
- a non-increasing timestamp producing an explicit continuity break without reordering input;
- independent epochs for distinct cgroup paths or container IDs;
- bounded active-epoch behavior and deterministic result ordering.

## Safety and non-goals

v0.7 reports measurements, eligibility, and quality only. It does not claim an OOM prediction,
confirmed memory leak, anomaly, workload diagnosis, safe remediation, or automatic action. PSI,
swap, cache, recommendations, backtesting, calibrated classifications, alerts, services, and a
dashboard remain outside this analyzer's scope.
